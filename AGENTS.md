# AGENTS.md

Repo of Dockerfiles for OpenCode agent images (published to GHCR via CI) plus an experimental Bun/TypeScript orchestrator under `orchestrator/`.

## Verification commands

- Orchestrator tests (only test suite in repo): `cd orchestrator && bun test`
  - Tests use fake CLI runners and temp dirs; no docker, network, or docker-helper needed.
- Type checking (from repo root): `tsc --noEmit -p orchestrator`. `bun test` does not type-check TypeScript.
  - Use a prepared development environment with TypeScript (`tsc`) on PATH and `@types/bun` resolvable by `orchestrator/tsconfig.json`; the repo has no package.json/lockfile or dependency-install step for these tools.
- CI (`.github/workflows/`) only plans/builds images — it does **not** run orchestrator tests. Run `bun test` locally before pushing.
- Shell/workflow checks (from repo root): `shellcheck scripts/*.sh gdk/*.sh`, `yamllint .github/`, `actionlint`. Preserve the existing targeted `# yamllint disable-line` markers in workflows.
- If required tools or dependencies are unavailable, report the affected checks as not run, not passed.

## Image build model

- Images are auto-discovered from root `Dockerfile_*` files; never edit a central list.
- `Dockerfile_base` defines the shared base and is exempt from dependent-image validation. Every other image must declare `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}`, or be marked `# ci: standalone` (currently `Dockerfile_gdk`); `scripts/build-images.sh plan` enforces this.
- `# ci: watch=<glob>` adds watched source paths; the Dockerfile itself is always watched. Changes under `.github/workflows/**`, `.github/actions/**`, `scripts/**`, or to `.dockerignore` trigger a rebuild of **all** images.
- Preserve selective, parallel builds: a changed base selects all dependents, not unchanged standalone images. Standalone jobs do not wait for base; selected dependents run in a matrix after base succeeds or is skipped. Empty selections must skip jobs before matrix expansion.
- PR builds must not log in to GHCR, publish images, or receive `packages: write`. Preserve the caller permission boundary in `.github/workflows/images.yml`; skipped login/push steps alone are not a token permission boundary.
- Local build of a dependent image requires `--build-arg BASE_IMAGE=...` (e.g. `ghcr.io/kivarun/opencode-docker/base:latest`); `build-images.sh build <name>` needs `EVENT_NAME`, `COMMIT_SHA`, and `REGISTRY_PREFIX` set.
- Bumping docker-helper means updating **both** `DOCKER_HELPER_VERSION` and `DOCKER_HELPER_SHA256` in `Dockerfile_base` (and `Dockerfile_gdk`, which pins it separately).

## Orchestrator (`orchestrator/`)

- Plain Bun TypeScript with **no package.json/lockfile**: Bun runs `src/main.ts` directly. Imports use explicit `.ts` extensions; type-only imports must use `import type` (`verbatimModuleSyntax`). Strict mode plus `noUncheckedIndexedAccess` — index access needs guards.
- Pipelines: `pipelines/default/` is the declarative pipeline bundle (schema version 1: `pipeline.yaml` + `prompts/` + `schemas/`); it is copied to `/opt/orchestrator/pipelines/default` by `Dockerfile_orchestrator` (`# ci: watch=pipelines/**`) and is now the **production input for `agent-smoke`**. `orchestrator/src/pipeline.ts` implements `parsePipelineSpec`/`loadPipeline` (loader + fail-closed validator) plus `planOneStepExecution`, the only supported execution shape: exactly one agent state whose single transition with outcome `completed` leads to a success terminal state, `max_transitions` 1, `max_attempts` 1, exactly one protected declared input, `timeout_seconds` within the single-timer bound (`MAX_RUN_TIMEOUT_SECONDS` = 2147483), and a `result_schema` that equals the standard agent result contract (`STANDARD_AGENT_RESULT_SCHEMA`, verbatim structural comparison). Any other structurally valid pipeline is rejected with a clear error before Launcher auth and before any child Session; multi-state graphs are never partially executed. Only `pipeline.yaml` is supported (never `.yml`/JSON); states/inputs/transitions are lists; the bundle root must be a directory and `pipeline.yaml` itself obeys the same canonical bundle containment as the other bundle files; workspace input paths must be unique (case-sensitive, lexical check only); the resolved pipeline carries the accepted `schema_version`. Arbitrary JSON Schema support, multi-state execution, retries, durable pipeline state, and resume are not implemented.
- Graph engine: `orchestrator/src/pipeline_engine.ts` implements `executePipelineGraph`, the pure, deterministic graph execution core and the **single owner of the outcome → transition → next-state mapping** (no parallel hand-written mapping). Before the first callback it compiles an immutable, engine-owned snapshot of exactly the graph data it needs (`entry_state`, `max_transitions`, state ids/types, terminal results, ordered transitions with original indices) and validates it fail-closed; during execution it reads transitions, terminal results, and the budget only from that snapshot, so mutations of the source `ResolvedPipeline` (sync in-callback or external while a callback is pending) cannot redirect the graph. The callback receives a separate frozen, deeply isolated, transition-free execution view (state id, profile, prompt, inputs, and a deep-cloned, recursively frozen JSON result schema — a corrupted non-JSON schema in an artificially damaged resolved pipeline is rejected `invalid_graph` before the callback) and returns only a validated outcome — it can never select the next state; free text/stdout/exit codes never participate. The engine resolves the declared transition by outcome itself and enforces `max_transitions` with a single reachable contract: an agent state cursor with an exhausted budget fails `transition_budget_exhausted` before the callback, and reaching a terminal exactly at the boundary succeeds. It finishes at a terminal state with `result: success|failed` (a `failed` terminal is a normal graph result, not an exception) and returns the terminal state id, terminal result, applied transition count, and an ordered transition trace (`from`, `outcome`, `to`, `transition_index`); no timestamps or randomness. Core supports sequential states, branching, and cycles bounded by `max_transitions`. It fails closed with `PipelineExecutionError` (stable reasons `invalid_graph`/`missing_state`/`unknown_outcome`/`invalid_outcome`/`transition_budget_exhausted`); a callback failure propagates unchanged — no transition recorded, cursor unmoved. Production `agent-smoke` runs its single step through this engine but stays restricted by `planOneStepExecution` (one child Session, one agent run, pre-auth rejection of multi-state graphs); multi-state worker execution, retries, durable state, resume, and concurrency are still not implemented, and the engine is not a second production path or a generic workflow engine.
- CLI: `bun src/main.ts smoke|agent-smoke`. `agent-smoke` takes `--config-root ABSOLUTE_PATH` and optional `--pipeline-root ABSOLUTE_PATH` (default `/opt/orchestrator/pipelines/default`), `--workspace`, `--launcher-id`; `--profile` and `--task` are removed — the execution profile and the workspace input path are selected only by the pipeline's agent state — and `--image` stays rejected (the image comes only from the selected profile). Plain `smoke` keeps `--image` and is unchanged. `agent-smoke` needs the docker-helper socket and a **Launcher** credential (never a Principal/admin credential) at `${XDG_CONFIG_HOME:-$HOME/.config}/docker-helper/credential.token`. Pipeline/plan/profile/input validation happens before Launcher auth: failures exit 1 with `runId: ""` and create no session.
- Agent worker input: the pipeline prompt travels only inside an orchestrator-owned execution document (`<run-dir>/execution.md`, non-secret: run id, state id, attempt, workspace-relative input/result paths, allowed outcome, prompt body, exact result format) written inside the existing run directory; the OpenCode command receives a short static instruction pointing at that document. Prompt and input bodies never appear in argv, env, state, or orchestrator diagnostics; the pipeline bundle and config root are not mounted into the worker. The pipeline's `timeout_seconds` is enforced only on the signalable worker `docker-helper run`: the runner sends SIGTERM at the deadline, marks the result timed out, and the run fails normally (exit 1, single cleanup); user SIGINT/SIGTERM keeps exit 130/143.
- docker-helper interaction: `session create/delete` and `pull`/`run` go through the **official CLI 2.1.0**, spawned as an argv array (`Bun.spawn`, no shell); the narrow `GET /auth` check stays a direct unix-socket call (the CLI has no equivalent Launcher-authority command). `session create/delete` run with a minimal filtered env (`HOME`, `XDG_CONFIG_HOME`, `XDG_RUNTIME_DIR`, `DOCKER_HELPER_CONFIG`); `pull`/`run` run with the child Session bearer only (`DOCKER_HELPER_SESSION_TOKEN`), which is repeated as `--env` so the worker receives its Session capability. Worker env values are passed as separate `--env KEY=VALUE` arguments; until docker-helper issue #3 is implemented, resolved worker env (including secrets and the OpenCode config content) is visible in the `docker-helper run` process argv — a consciously accepted temporary risk. They never appear in state files or the orchestrator's own diagnostics. Worker output is inherited from the CLI process: docker-helper 2.1.0 prints the (already mixed) container operation output on its stdout, and the CLI's own warnings/errors go to stderr; raw worker output is treated as untrusted (never a safe audit log or authoritative state); the orchestrator implements no polling, log cursor, or operation-API parsing.
- Cancellation contract: the first SIGINT/SIGTERM is recorded by the lifecycle; a running `docker-helper run` process receives the same signal (a bounded synchronous best-effort cancel inside docker-helper 2.1.0 — the orchestrator never confirms a terminal operation state) under a first-wins rule: the first terminal cause of the active signalable worker — runner `timeout` or `user_signal` — is recorded once; a user signal that wins suppresses the timer (`timedOut` stays false, exit 130/143), and a user signal that loses to the runner timer is neither delivered nor forwarded to the lifecycle (the run stays a timeout failure, exit 1). `killActive` returns whether the signal may still be recorded as a lifecycle abort; signals outside a worker run keep the plain lifecycle semantics. `session create`, `pull`, and `session delete` always run to completion. Cleanup (child Session delete) happens only in the single lifecycle `finally`, after the active hook settles — no fire-and-forget cleanup. Signal acceptance closes in the same synchronous tail that completes the authoritative final state write; a signal accepted while that write was in flight rewrites a persisted `success` to `failed`, and a signal delivered after the write completes can no longer change the recorded outcome or the exit code.
- `--workspace` is the absolute host workspace path used by docker-helper; it must also be visible at that same absolute path inside the orchestrator container (the proven dual-mount pattern: mount the Session workspace twice — canonical host path + `/workspace`). Workers mount the Session workspace at `/workspace` (`source "."`); the host path need not be reproduced inside workers. A helper-launched container cannot receive the docker-helper socket (workspace-relative sources only), so a containerized orchestrator must be launched by the operator (plain `docker run` with socket + credential + dual mounts); this docker-helper limitation blocks the helper-launched UAT path until helper gains trusted socket projection.

## Hard invariants

- Never mount `docker.sock` into the orchestrator or agent containers; docker-helper is the only Docker access path.
- Images must not bake in provider credentials or OpenCode model config.
- The agent worker env is built from **exact bindings declared by the selected trusted profile** (`orchestrator/src/profile.ts`), plus explicit orchestrator-owned run params (`OPENCODE_CONFIG_CONTENT` from the profile's OpenCode config, the child session bearer, `AGENT_SMOKE_*` run identity). No ambient inheritance. Control variables (`DOCKER_HELPER_*`, `AGENT_SMOKE_*`, `ORCHESTRATOR_*`, `OPENCODE_CONFIG_CONTENT`) and operator path variables (`HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`) can be neither profile destinations nor sources; launcher credentials, admin tokens, and the orchestrator state path are never forwarded. Keep `orchestrator/src/main.ts` usage text and tests in sync when touching the contract.
- For `agent-smoke`, exit code 0 or agent JSON events alone never mean success: validate the `result.json` schema (exact fields only), `run_id`, artifact existence and workspace confinement (including symlinks), unchanged protected input, and the outcome transition to a success terminal before accepting the result.
- Every created child Session must be cleaned up on all controlled exit paths, including errors and cancellation. Cleanup failure makes the overall run unsuccessful, even when the worker succeeded.
- Trusted execution profiles: implementation and deterministic tests are complete; the end-to-end profile-backed `agent-smoke` UAT (real launcher credential, real docker-helper, real OpenCode/LLM run) is still pending. Do not describe profiles as a proven baseline in docs until that UAT passes.
- `base`/`go26`/`dotnet10`/`orchestrator` run as non-root `opencode` user (uid/gid 1000); `gdk` follows its upstream GDK image user model.
