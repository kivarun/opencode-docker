# AGENTS.md

Repo of Dockerfiles for OpenCode agent images (published to GHCR via CI) plus an experimental Bun/TypeScript orchestrator under `orchestrator/`.

## Verification commands

- Orchestrator tests (only test suite in repo): `cd orchestrator && bun test`
  - Tests use fake CLI runners and temp dirs; no docker, network, or docker-helper needed.
- Type checking (from repo root): `tsc --noEmit -p orchestrator`. `bun test` does not type-check TypeScript.
  - `orchestrator/package.json` + `orchestrator/bun.lock` pin all orchestrator dependencies (runtime: `ajv` 8.17.1; dev: `@types/bun` 1.4.1 with an `overrides` pin on `@types/node` 26.5.0). Install them with `cd orchestrator && bun install --frozen-lockfile` (needs `orchestrator/node_modules`, which is gitignored and never committed). Type checking additionally needs a prepared environment with `tsc` on PATH.
- CI (`.github/workflows/`) only plans/builds images — it does **not** run orchestrator tests. Run `bun test` locally before pushing.
- Shell/workflow checks (from repo root): `shellcheck scripts/*.sh gdk/*.sh`, `yamllint .github/`, `actionlint`. Preserve the existing targeted `# yamllint disable-line` markers in workflows.
- If required tools or dependencies are unavailable, report the affected checks as not run, not passed.

## Image build model

- Images are auto-discovered from root `Dockerfile_*` files; never edit a central list.
- `Dockerfile_base` defines the shared base and is exempt from dependent-image validation. Every other image must declare `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}`, or be marked `# ci: standalone` (currently `Dockerfile_gdk`); `scripts/build-images.sh plan` enforces this.
- `# ci: watch=<glob>` adds watched source paths; the Dockerfile itself is always watched. Changes under `.github/workflows/**`, `.github/actions/**`, `scripts/**`, or to `.dockerignore` trigger a rebuild of **all** images.
- Preserve selective, parallel builds: a changed base selects all dependents, not unchanged standalone images. Standalone jobs do not wait for base; selected dependents run in a matrix after base succeeds or is skipped. Empty selections must skip jobs before matrix expansion.
- PR builds must not log in to GHCR, publish images, or receive `packages: write`. Preserve the caller permission boundary in `.github/workflows/images.yml`; skipped login/push steps alone are not a token permission boundary.
- Local build of a dependent image requires `--build-arg BASE_IMAGE=...` (e.g. `ghcr.io/kivarun/opencode-docker/base:latest`); `build-images.sh build <name>` needs `EVENT_NAME`, `COMMIT_SHA`, and `REGISTRY_PREFIX` set.
- Bumping docker-helper means updating **both** `DOCKER_HELPER_VERSION` and `DOCKER_HELPER_SHA256` in `Dockerfile_base` (and `Dockerfile_gdk`, which pins it separately).

## Orchestrator (`orchestrator/`)

- Plain Bun TypeScript: Bun runs `src/main.ts` directly. `orchestrator/package.json` + `orchestrator/bun.lock` pin the runtime dependencies (`ajv`); imports use explicit `.ts` extensions; type-only imports must use `import type` (`verbatimModuleSyntax`). Strict mode plus `noUncheckedIndexedAccess` — index access needs guards.
- Pipelines: `pipelines/default/` is the declarative pipeline bundle (schema version 1: `pipeline.yaml` + `prompts/` + `schemas/`); it is copied to `/opt/orchestrator/pipelines/default` by `Dockerfile_orchestrator` (`# ci: watch=pipelines/**`) and is now the **production input for `agent-smoke`**. `orchestrator/src/pipeline.ts` implements `parsePipelineSpec`/`loadPipeline` (loader + fail-closed validator) plus `planMultiStateExecution`, the only supported execution shape: any number of agent and terminal states, an agent or terminal entry state, cycles within `max_transitions`, `max_attempts` 1, exactly one transition per agent state with outcome `completed`, `timeout_seconds` within the single-timer bound (`MAX_RUN_TIMEOUT_SECONDS` = 2147483), and a `result_schema` that equals the standard multi-state agent result contract (`STANDARD_AGENT_RESULT_SCHEMA`, verbatim structural comparison). Terminal states may sit beyond the reachable part of the graph (a cycle can never leave itself; the budget bounds the run). Any other structurally valid pipeline — extra transitions, foreign outcomes, retries, custom decision payloads — is rejected with a clear error before Launcher auth and before any child Session; unsupported graphs are never partially executed. Only `pipeline.yaml` is supported (never `.yml`/JSON); states/inputs/transitions are lists; the bundle root must be a directory and `pipeline.yaml` itself obeys the same canonical bundle containment as the other bundle files; workspace input paths must be unique (case-sensitive, lexical check only); the resolved pipeline carries the accepted `schema_version`. All declared profiles load and validate before auth; agent states must be reachable from the entry state, unreachable terminal states are tolerated. Arbitrary JSON Schema support, content-based branching, retries, and resume are not implemented.
- Graph engine: `orchestrator/src/pipeline_engine.ts` implements the pure, deterministic graph execution core — **one** execution loop (`runCompiledGraph`) and the **single owner of the outcome → transition → next-state mapping** (no parallel hand-written mapping) for both pipeline versions. Version-specific compilation adapters (`compileV1Graph` over `ResolvedPipeline`, `compileV2Graph` over the provenance-checked `ResolvedPipelineV2`) each build the same internal engine-owned snapshot; there is no second execution machine. Before the first callback it compiles an immutable, engine-owned snapshot of exactly the graph data it needs (`entry_state`, `max_transitions`, state ids/types, terminal results, ordered transitions with original indices) and validates it fail-closed; during execution it reads transitions, terminal results, and the budget only from that snapshot, so mutations of the source pipeline (sync in-callback or external while a callback is pending) cannot redirect the graph. For a v1 agent state the callback receives a separate frozen, deeply isolated, transition-free execution view (state id, profile, prompt, inputs, and a deep-cloned, recursively frozen JSON result schema — a corrupted non-JSON schema in an artificially damaged resolved pipeline is rejected `invalid_graph` before the callback); for a v2 agent/decision state the frozen views are the exact `V2AgentExecutionView`/`V2DecisionExecutionView` compiled at snapshot time (no transitions, targets, transition indexes, data ports, schemas, or credentials). A v2 agent callback returns nothing: after it resolves, the engine applies the fixed lifecycle outcome `completed` (`AGENT_COMPLETED_OUTCOME`, compile-time constant) from its own compiled snapshot — the callback value returned against the void contract is dropped and never reaches transition selection; only a decision executor still reports a validated outcome. Neither executor can ever select the next state; free text/stdout/exit codes never participate. The dispatch is compile-time-bound per state (`agent` → `executeAgent` only, `decision` → `executeDecision` only, `terminal` → no callback). The engine resolves the declared transition by outcome itself and enforces `max_transitions` with a single reachable contract: a transition-bearing cursor with an exhausted budget fails `transition_budget_exhausted` before the callback (agent and decision states share one budget; the message names `agent state`/`decision state` explicitly), and reaching a terminal exactly at the boundary succeeds. It finishes at a terminal state with `result: success|failed` (a `failed` terminal is a normal graph result, not an exception) and returns the terminal state id, terminal result, applied transition count, and an ordered transition trace (`from`, `outcome`, `to`, `transition_index`); no timestamps or randomness. Core supports sequential states, branching, and cycles bounded by `max_transitions`. It fails closed with `PipelineExecutionError` (stable reasons `invalid_graph`/`missing_state`/`unknown_outcome`/`invalid_outcome`/`invalid_executor`/`transition_budget_exhausted`); a callback failure propagates unchanged — no transition recorded, cursor unmoved. The v2 entry point `executePipelineV2Graph(pipeline, executors, options?)` first runs the existing `requireResolvedPipelineV2Provenance` gate (clones/casts/spreads/Proxies rejected before any content read or callback), then captures both executor functions exactly once into an engine-owned frozen snapshot — a missing or non-function executor fails `invalid_executor` before graph compilation and before any callback, and reassigning the caller's object mid-run cannot change the dispatch — and only then compiles the shared snapshot; `PipelineV2GraphExecutors` is `{ executeAgent: (state: V2AgentExecutionView) => void | Promise<void>; executeDecision: (state: V2DecisionExecutionView) => string | Promise<string> }` — the engine never parses decision facts or knows the decision table (the production runner closes the trusted pipeline/run data over `executeDecision`, e.g. via `evaluateDecisionStateFromData(...).outcome`), and a defensive `compileV2AgentContract` guard repeats the loader's agent-state contract (`invalid_graph`: exactly one transition with outcome `completed`, `max_attempts` exactly 1) against an internally damaged agent state before the first callback. `orchestrator/tests/pipeline_v2_engine.test.ts` covers the v2 dispatch battery (agent→decision, entry decision, entry terminal, reserved-outcome routing, decision chains, agent/decision cycles with exit, budget exhaustion before the decision callback with the `decision state ... cannot execute` message and before the next agent callback with the `agent state ... cannot execute` message, boundary terminals, rogue agent-callback return values (strings, objects, numbers, async promises — all ignored, `completed` still applied), invalid decision outcomes, cross-dispatch exclusivity, callback exception identity, hook ordering/failure, exact trace indexes, frozen transition-free views, in-callback and pending-callback mutation attempts (frozen trusted snapshot + snapshot-bound engine), clone/spread/Proxy provenance rejection before any callback or getter trap, and an integration run whose decision executor is the real `evaluateDecisionStateFromData` routing its selected outcome through the shared core to the declared terminal). Production `agent-smoke` runs every step through this engine under `planMultiStateExecution`; multi-state worker execution **is** implemented (see below), while retries, resume, and concurrency are still not, and the engine is not a second production path or a generic workflow engine.
- Durable pipeline run state (schema version 2, implemented): `agent-smoke` records one authoritative, atomically committed JSON document per run at `<XDG state root>/pipeline-runs/<run-id>/state.json`. Modules: `pipeline_state.ts` (versioned contract + exact-field validator + pure reducer), `pipeline_state_store.ts` (durable store + injectable `PipelineStateIo` seam), `pipeline_state_sink.ts` (production `RunStateSink`), `pipeline_digest.ts` (canonical-JSON execution snapshot digest), `run_errors.ts` (`AgentTimeoutError`/`WorkspaceInputError`/`RuntimeInputError`, normalized text-free failure reasons). Write protocol per commit: ensureDir 0700, reject symlinked run dirs, `O_EXCL` temp file 0600, fsync file, atomic rename over `state.json`, fsync dir, unlink temp on pre-rename failure; `create` refuses to overwrite, `commit` verifies the on-disk revision matches and the new revision is exactly +1. Commit outcomes are typed: `not_committed` (`PipelineStateStoreError`) — the rename did not happen, the previous snapshot remains authoritative byte-for-byte; `durability_unknown` (`PipelineStateDurabilityError`, carries the candidate revision + snapshot) — the rename succeeded but the post-rename directory fsync failed, so the candidate is already visible while its crash survival is unknown; the sink adopts the candidate, poisons itself (no further commits or finalize), and the run fails with exit 1 and exactly one cleanup — no rollback, no recovery, and the previous snapshot is never claimed to have survived. The state records identity/status/phase, pipeline identity (bundle root excluded from the digest input), all protected inputs with their digests, the ordered activations (global monotonic index from 1, state id, attempt 1, profile, activation phase, session id after create, cleanup outcome, accepted result digest + artifact paths, normalized activation failure), transitions referencing their activation (`transition_index` is the engine's per-state original index), the shared cursor + transition count, the terminal, a normalized failure reason, and an ordered discriminated event journal (events carry `state_id`/`activation_index`/`session_id`/`transition_index` where relevant); it never records credentials, env values, prompt/input bodies, OpenCode config, result summaries, or worker output. There is **no v1 migration**: the loader rejects v1 as an unsupported version, old files are never rewritten. The reducer enforces event successor rules and cursor/transition/activation coherence (contiguous activation indexes, one active activation, a new activation only after the previous activation's cleanup and transition, a transition references the accepted-and-cleaned activation whose `from` equals the cursor, a transition that would exceed `pipeline.max_transitions` is rejected, terminal only at the cursor, a terminal cannot be reached after a cleaned activation whose transition was never committed, terminal run status immutable — no post-success or post-failure mutations, no `success → failed` rewrite). The loader enforces the same coherence fail-closed: `transitions.length > pipeline.max_transitions` is rejected, every event payload (`state_id`, `activation_index`, `session_id`, transition `from`/`outcome`/`to`/`transition_index`, terminal `state_id`) must name exactly the activation, session, transition, or terminal record it belongs to, and an entry-terminal run with zero activations and transitions stays representable. An activation may record both an accepted result digest and a later failure reason (e.g. the session cleanup failed right after acceptance). The engine transition-commit hook is the only transition recorder: a `not_committed` hook failure leaves no recorded transition and an unmoved cursor; a `durability_unknown` hook failure may leave the new candidate revision visible on disk, but execution stops immediately either way and the run fails with exit 1. If the initial snapshot never committed, finalize still records the run so failures are durable. Plain `smoke` keeps its legacy flat state byte-for-byte (`LegacyRunStateSink`, no-op initialize). Not implemented: resume, multi-process locking, schema migration, run listing, post-rename durability recovery.
- Durable pipeline v2 run state (state schema version 6, pure substrate, wired into the production runner): `orchestrator/src/pipeline_v2_state.ts` implements the future pipeline-v2 durable state as a self-contained pure module — `PIPELINE_V2_RUN_STATE_SCHEMA_VERSION = 6`, `reducePipelineV2RunCommand` (pure reducer returning independent deep-frozen snapshots; input state and command are never mutated), `validatePipelineV2RunState`, and `parsePipelineV2RunState` (content-free malformed-JSON diagnostic, no parser fragments; explicit rejection of state schema versions 1, 2, 3, 4 and 5 with no migration in either direction; stored v5 files are never rewritten and stay byte-for-byte unchanged). The nested pipeline identity must carry `schema_version: 2`. v6 intentionally has **no `events[]`**: `executions`, `transitions`, `waits`, `terminal`, and `run_outputs` are the single authoritative journal, and the loader re-derives cursor/transition/terminal/output coherence from those records alone (no second event model, no bidirectional event/record coherence layer, no separate response journal, no current-wait pointer). Schema v6 adds the durable user-response successor for the user wait and replaces the v5 single optional top-level `wait` record with the required wait journal `waits` — an ordered list of content-free `PipelineV2WaitRecord {index, transition_count, state_id, reason, request_sha256, actions, response?}` entries where `index` is contiguous from 1, `transition_count` is the number of committed graph transitions at the moment the run entered the wait, `state_id`/`reason` and every `actions[].id`/`.to` obey the shared `expectSafeId` grammar, `request_sha256`/`response_sha256` are lowercase 64-hex digests reserving the link to future orchestrator-owned user request/response manifests (manifests and their data-plane publication, manifest validation, and the policy/controller layer that validates user intent are later increments — the reducer trusts only an already validated command), `actions` is a non-empty list with unique ids in preserved declaration order where several ids may share one target, and the optional content-free `response` record `{action_id, response_sha256}` references only an action declared in the same record (the routing target is always the declared `to`, never duplicated); no paths, evidence bodies, TASK/PLAN content, facts, prompts, worker output, env values, profiles or credentials anywhere in the document. The 20-command union adds exactly one command: `run_waiting {stateId, reason, requestSha256, actions}` now **appends** a new open record (index `waits.length + 1`, `transition_count` from the cursor) on the same clean boundary as before (active `running` run, cursor match, no terminal/outputs/failure, all executions settled and fully committed, no open wait), setting `status`/`phase` to `waiting`; `wait_response_recorded {waitIndex, expectedRequestSha256, actionId, responseSha256}` is accepted only on a `waiting` run whose last wait record is open and is exactly `waitIndex` with the matching request digest and a declared action id — it atomically closes that record with the response, returns the run to `active`/`running`, and moves `cursor.current_state` to the declared action target without touching `transition_count`, `max_transitions`, executions, transitions or prior history (no execution/transition/session is created); after the response ordinary commands apply again under the existing successor rules, a new execution gets the next global index, identities are never reused, and a repeated wait is valid on the next clean boundary (several wait/response cycles, including several waits at one `transition_count`). The loader restores the cursor by a joint replay of both authoritative streams: starting at `pipeline.entry_state`, before every graph transition with ordinal N+1 it applies in order all waits with `transition_count === N`; each wait must name the replay cursor; a response moves the replay cursor to the declared action target; an open record may only end the journal (no later waits, no executions or transitions after it, fully settled and committed history) and pins the cursor at its state; every graph transition must start at the replay cursor; the persisted cursor must equal the replayed cursor and `cursor.transition_count === transitions.length` (wait/response never consume graph budget); the execution ↔ graph-transition coherence is unchanged and a user response is never a fictitious execution or transition. The loader enforces the triple biconditional (`status === "waiting"` ⇔ `phase === "waiting"` ⇔ the last wait record exists and is open), waiting forbidding terminal/run_outputs/failure, and rejects final states with an open wait; both sides accept exactly the same state set. Two-session capability model: one agent execution durably records two independent session ids — `execution_session_id` (the orchestrator-owned Execution Session, scope run root, never handed to the worker) and `tool_session_id` (the Tool Session, scope project, its bearer is the worker's only authority) — plus `session_cleanup` as an independent pair `{execution, tool}` of `not_required`|`completed`|`failed`; Transitions (`index` = the engine's original per-state transition index, `from`/`outcome`/`to`, `execution_index`) bind exactly the last settled execution — agent after `cleanup_completed`, decision after `evaluated` with the recorded outcome equal to the transition outcome — and move the cursor to `to` only; run outputs carry `present`/`digest` only (location fixed at `<runRoot>/outputs/<id>`), and no run root, project root, snapshot paths, activation paths, user binding paths, or prompt/fact bodies exist anywhere in the document. - Pipeline v2 run-input snapshots + activation data layout (pure host-side substrate, used by the production runner through the coordinator, no Session/container launch itself): `orchestrator/src/pipeline_v2_runtime.ts` is the v2 data plane. Run layout: `<runRoot>/project` is the shared project directory of the whole run — the coordinator prepares the run-owned copy from the caller's source directory via `prepareRunProject(projectSourcePath, runRoot)`, and every activation mounts exactly this one directory at `/workspace` read-write, so changes persist across activations; there is no per-activation project directory. `prepareRunProject(projectSourcePath, runRoot) -> PreparedRunProject` (deep-frozen `{run_root, project_root}`; the source path is deliberately not part of the object): the caller hands over only the source directory path — the source is never modified, renamed, cleared or read beyond this copy, its path never enters the pipeline, execution document, worker env/argv, durable state or results, and the internal run-root layout is not presented to the user. `runRoot` must be an existing absolute canonical real non-symlink directory (`realpath(runRoot) === runRoot`; never created or removed by the function); `<runRoot>/project` must be absent as an object of any kind (a repeated call fails closed and never overwrites); the source must be an absolute real non-symlink directory whose canonical path is fixed before copying, and source/runRoot must not overlap in either direction. The `run` branch is taken before the v1 helper-config resolution: inside `runPipelineV2Command` the state-root projection is resolved first and the helper configuration second, both inside one protected CLI-configuration boundary — any failure (including the real `resolveHelperConfig` with no `HOME`/`XDG_CONFIG_HOME`) is a CLI configuration error (exit 2 with usage) with no `runPipelineV2` call, no auth, no filesystem, no runner subprocess, no signal registration, and `runCli` never rejects; the shared v1 `resolveHelperConfig` call still runs only for `smoke`/`agent-smoke` with unchanged behavior. Human mode prints exactly one stderr summary line — success `orchestrator: run ok (run <RUN_ID>, state <RUN_ROOT>/state.json, outputs <RUN_ROOT>/outputs)`, post-run-root failure `orchestrator: run failed (run <RUN_ID>, reason <REASON>, state <RUN_ROOT>/state.json)` (no summary line until the run root exists; the runner's content-free diagnostics carry pre-root failures) — and returns the outcome's `exitCode`. `--json` writes exactly one JSON `PipelineV2RunOutcome` document plus a trailing newline to stdout (no extra wrapper, machine-readable for success and failure, content-free), keeps stdout free of progress lines by switching only the inherit-asked CLI calls (image pull, worker run) to the streaming `stderr` `CliStdio` mode — the child's stdout and stderr flow directly onto the orchestrator's stderr at kernel level (`Bun.spawn` fd 2), with no buffering, no accumulation and no post-hoc forwarding; `capture` calls (structured session answers) stay captured and human mode keeps the adapter's `inherit` (argv, env, options and every runtime decision untouched), and the CLI exits with the outcome's `exitCode`. Run outputs stay at the fixed `<runRoot>/outputs`; the CLI reports but never relocates them. `usage()` documents the run command (required flags, repeatable `--input`, run-owned project copy, fixed state/outputs locations, the two state-root env variables, profiles-selected-by-pipeline-states, no user mounts/paths/credentials/helper transport) and no longer claims `agent-smoke` is one-step only — its production v1 runner is multi-state; `docs/orchestration-workflow.md` was synced to the implemented state. Tests: `tests/cli.test.ts` (run parser battery + updated usage pins; smoke/agent-smoke parsing unchanged), `tests/pipeline_v2_state_root.test.ts` (11 resolver tests incl. every unclean form through all four env sources), `tests/cli_main.test.ts` (18 dispatcher tests with per-call fakes: exact single dispatch and options mapping, resolver-failure exit 2, exit-code passthrough 0/1/130/143, pre-run-root silence, the JSON single-document contract with canary scans, JSON capture-to-stderr plumbing, unchanged v1 routing for `smoke`/`agent-smoke`). ## Hard invariants

- Never mount `docker.sock` into the orchestrator or agent containers; docker-helper is the only Docker access path.
- Images must not bake in provider credentials or OpenCode model config.
- The agent worker env is built from **exact bindings declared by the selected trusted profile** (`orchestrator/src/profile.ts`), plus explicit orchestrator-owned run params (`OPENCODE_CONFIG_CONTENT` from the profile's OpenCode config, the child session bearer, `AGENT_SMOKE_*` run identity). No ambient inheritance. Control variables (`DOCKER_HELPER_*`, `AGENT_SMOKE_*`, `ORCHESTRATOR_*`, `OPENCODE_CONFIG_CONTENT`) and operator path variables (`HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`) can be neither profile destinations nor sources; launcher credentials, admin tokens, and the orchestrator state path are never forwarded. Keep `orchestrator/src/main.ts` usage text and tests in sync when touching the contract.
- For `agent-smoke`, exit code 0 or agent JSON events alone never mean success: validate the per-activation `result.json` schema (exact fields only, schema version 2), the `run_id`/`state_id`/`activation_index`/`attempt` identity, artifact existence and workspace confinement (including symlinks), unchanged protected inputs, and the outcome transition to a success terminal before accepting the result.
- Every created child Session must be cleaned up on all controlled exit paths, including errors and cancellation. Cleanup failure makes the overall run unsuccessful, even when the worker succeeded.
- Trusted execution profiles: implementation, deterministic tests and the end-to-end profile-backed `agent-smoke` UAT (real launcher credential, real docker-helper, real OpenCode/LLM run, `local/glm53-flash`, report from 2026-09-11) are complete; the UAT verified the full v1 path including durable state, cleanup and secret containment.
- `base`/`go26`/`dotnet10`/`orchestrator` run as non-root `opencode` user (uid/gid 1000); `gdk` follows its upstream GDK image user model.
