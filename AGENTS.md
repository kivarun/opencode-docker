# AGENTS.md

Repo of Dockerfiles for OpenCode agent images (published to GHCR via CI) plus an experimental Bun/TypeScript orchestrator under `orchestrator/`.

## Verification commands

- Orchestrator tests (only test suite in repo): `cd orchestrator && bun test`
  - Tests use fake CLI runners and temp dirs; no docker, network, or docker-helper needed.
- Type checking (from repo root): `tsc --noEmit -p orchestrator`. `bun test` does not type-check TypeScript.
  - `orchestrator/package.json` + `orchestrator/bun.lock` pin all orchestrator dependencies (runtime: `ajv` 8.17.1; dev: `@types/bun` 1.4.1 with an `overrides` pin on `@types/node` 26.5.0). Install them with `cd orchestrator && bun install --frozen-lockfile` (needs `orchestrator/node_modules`, which is gitignored and never committed). Type checking additionally needs a prepared environment with `tsc` on PATH.
- CI (`.github/workflows/`) only plans/builds images — it does **not** run orchestrator tests. Run `bun test` locally before pushing.
- Shell/workflow checks (from repo root): `shellcheck scripts/*.sh gdk/*.sh`, `yamllint .github/`, `actionlint`. Preserve the existing targeted `# yamllint disable-line` markers in workflows.
- If required tools or dependencies are unavailable, report the affected checks as not run, not passed.

## Image build model

- Images are auto-discovered from root `Dockerfile_*` files; never edit a central list.
- `Dockerfile_base` defines the shared base and is exempt from dependent-image validation. Every other image must declare `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}`, or be marked `# ci: standalone` (currently `Dockerfile_gdk`); `scripts/build-images.sh plan` enforces this.
- `# ci: watch=<glob>` adds watched source paths; the Dockerfile itself is always watched. Changes under `.github/workflows/**`, `.github/actions/**`, `scripts/**`, or to `.dockerignore` trigger a rebuild of **all** images.
- Preserve selective, parallel builds: a changed base selects all dependents, not unchanged standalone images. Standalone jobs do not wait for base; selected dependents run in a matrix after base succeeds or is skipped. Empty selections must skip jobs before matrix expansion.
- PR builds must not log in to GHCR, publish images, or receive `packages: write`. Preserve the caller permission boundary in `.github/workflows/images.yml`; skipped login/push steps alone are not a token permission boundary.
- Local build of a dependent image requires `--build-arg BASE_IMAGE=...` (e.g. `ghcr.io/kivarun/opencode-docker/base:latest`); `build-images.sh build <name>` needs `EVENT_NAME`, `COMMIT_SHA`, and `REGISTRY_PREFIX` set.
- Bumping docker-helper means updating **both** `DOCKER_HELPER_VERSION` and `DOCKER_HELPER_SHA256` in `Dockerfile_base` (and `Dockerfile_gdk`, which pins it separately).

## Orchestrator (`orchestrator/`)

- Plain Bun TypeScript: Bun runs `src/main.ts` directly. `orchestrator/package.json` + `orchestrator/bun.lock` pin the runtime dependencies (`ajv`); imports use explicit `.ts` extensions; type-only imports must use `import type` (`verbatimModuleSyntax`). Strict mode plus `noUncheckedIndexedAccess` — index access needs guards.
- Pipelines: `pipelines/default/` is the declarative pipeline bundle (schema version 1: `pipeline.yaml` + `prompts/` + `schemas/`); it is copied to `/opt/orchestrator/pipelines/default` by `Dockerfile_orchestrator` (`# ci: watch=pipelines/**`) and is now the **production input for `agent-smoke`**. `orchestrator/src/pipeline.ts` implements `parsePipelineSpec`/`loadPipeline` (loader + fail-closed validator) plus `planMultiStateExecution`, the only supported execution shape: any number of agent and terminal states, an agent or terminal entry state, cycles within `max_transitions`, `max_attempts` 1, exactly one transition per agent state with outcome `completed`, `timeout_seconds` within the single-timer bound (`MAX_RUN_TIMEOUT_SECONDS` = 2147483), and a `result_schema` that equals the standard multi-state agent result contract (`STANDARD_AGENT_RESULT_SCHEMA`, verbatim structural comparison). Terminal states may sit beyond the reachable part of the graph (a cycle can never leave itself; the budget bounds the run). Any other structurally valid pipeline — extra transitions, foreign outcomes, retries, custom decision payloads — is rejected with a clear error before Launcher auth and before any child Session; unsupported graphs are never partially executed. Only `pipeline.yaml` is supported (never `.yml`/JSON); states/inputs/transitions are lists; the bundle root must be a directory and `pipeline.yaml` itself obeys the same canonical bundle containment as the other bundle files; workspace input paths must be unique (case-sensitive, lexical check only); the resolved pipeline carries the accepted `schema_version`. All declared profiles load and validate before auth; agent states must be reachable from the entry state, unreachable terminal states are tolerated. Arbitrary JSON Schema support, content-based branching, retries, and resume are not implemented.
- Graph engine: `orchestrator/src/pipeline_engine.ts` implements `executePipelineGraph`, the pure, deterministic graph execution core and the **single owner of the outcome → transition → next-state mapping** (no parallel hand-written mapping). Before the first callback it compiles an immutable, engine-owned snapshot of exactly the graph data it needs (`entry_state`, `max_transitions`, state ids/types, terminal results, ordered transitions with original indices) and validates it fail-closed; during execution it reads transitions, terminal results, and the budget only from that snapshot, so mutations of the source `ResolvedPipeline` (sync in-callback or external while a callback is pending) cannot redirect the graph. The callback receives a separate frozen, deeply isolated, transition-free execution view (state id, profile, prompt, inputs, and a deep-cloned, recursively frozen JSON result schema — a corrupted non-JSON schema in an artificially damaged resolved pipeline is rejected `invalid_graph` before the callback) and returns only a validated outcome — it can never select the next state; free text/stdout/exit codes never participate. The engine resolves the declared transition by outcome itself and enforces `max_transitions` with a single reachable contract: an agent state cursor with an exhausted budget fails `transition_budget_exhausted` before the callback, and reaching a terminal exactly at the boundary succeeds. It finishes at a terminal state with `result: success|failed` (a `failed` terminal is a normal graph result, not an exception) and returns the terminal state id, terminal result, applied transition count, and an ordered transition trace (`from`, `outcome`, `to`, `transition_index`); no timestamps or randomness. Core supports sequential states, branching, and cycles bounded by `max_transitions`. It fails closed with `PipelineExecutionError` (stable reasons `invalid_graph`/`missing_state`/`unknown_outcome`/`invalid_outcome`/`transition_budget_exhausted`); a callback failure propagates unchanged — no transition recorded, cursor unmoved. Production `agent-smoke` runs every step through this engine under `planMultiStateExecution`; multi-state worker execution **is** implemented (see below), while retries, resume, and concurrency are still not, and the engine is not a second production path or a generic workflow engine.
- Durable pipeline run state (schema version 2, implemented): `agent-smoke` records one authoritative, atomically committed JSON document per run at `<XDG state root>/pipeline-runs/<run-id>/state.json`. Modules: `pipeline_state.ts` (versioned contract + exact-field validator + pure reducer), `pipeline_state_store.ts` (durable store + injectable `PipelineStateIo` seam), `pipeline_state_sink.ts` (production `RunStateSink`), `pipeline_digest.ts` (canonical-JSON execution snapshot digest), `run_errors.ts` (`AgentTimeoutError`/`WorkspaceInputError`/`RuntimeInputError`, normalized text-free failure reasons). Write protocol per commit: ensureDir 0700, reject symlinked run dirs, `O_EXCL` temp file 0600, fsync file, atomic rename over `state.json`, fsync dir, unlink temp on pre-rename failure; `create` refuses to overwrite, `commit` verifies the on-disk revision matches and the new revision is exactly +1. Commit outcomes are typed: `not_committed` (`PipelineStateStoreError`) — the rename did not happen, the previous snapshot remains authoritative byte-for-byte; `durability_unknown` (`PipelineStateDurabilityError`, carries the candidate revision + snapshot) — the rename succeeded but the post-rename directory fsync failed, so the candidate is already visible while its crash survival is unknown; the sink adopts the candidate, poisons itself (no further commits or finalize), and the run fails with exit 1 and exactly one cleanup — no rollback, no recovery, and the previous snapshot is never claimed to have survived. The state records identity/status/phase, pipeline identity (bundle root excluded from the digest input), all protected inputs with their digests, the ordered activations (global monotonic index from 1, state id, attempt 1, profile, activation phase, session id after create, cleanup outcome, accepted result digest + artifact paths, normalized activation failure), transitions referencing their activation (`transition_index` is the engine's per-state original index), the shared cursor + transition count, the terminal, a normalized failure reason, and an ordered discriminated event journal (events carry `state_id`/`activation_index`/`session_id`/`transition_index` where relevant); it never records credentials, env values, prompt/input bodies, OpenCode config, result summaries, or worker output. There is **no v1 migration**: the loader rejects v1 as an unsupported version, old files are never rewritten. The reducer enforces event successor rules and cursor/transition/activation coherence (contiguous activation indexes, one active activation, a new activation only after the previous activation's cleanup and transition, a transition references the accepted-and-cleaned activation whose `from` equals the cursor, a transition that would exceed `pipeline.max_transitions` is rejected, terminal only at the cursor, a terminal cannot be reached after a cleaned activation whose transition was never committed, terminal run status immutable — no post-success or post-failure mutations, no `success → failed` rewrite). The loader enforces the same coherence fail-closed: `transitions.length > pipeline.max_transitions` is rejected, every event payload (`state_id`, `activation_index`, `session_id`, transition `from`/`outcome`/`to`/`transition_index`, terminal `state_id`) must name exactly the activation, session, transition, or terminal record it belongs to, and an entry-terminal run with zero activations and transitions stays representable. An activation may record both an accepted result digest and a later failure reason (e.g. the session cleanup failed right after acceptance). The engine transition-commit hook is the only transition recorder: a `not_committed` hook failure leaves no recorded transition and an unmoved cursor; a `durability_unknown` hook failure may leave the new candidate revision visible on disk, but execution stops immediately either way and the run fails with exit 1. If the initial snapshot never committed, finalize still records the run so failures are durable. Plain `smoke` keeps its legacy flat state byte-for-byte (`LegacyRunStateSink`, no-op initialize). Not implemented: resume, multi-process locking, schema migration, run listing, post-rename durability recovery.
- Multi-state execution and activation/session order (implemented): `orchestrator/src/pipeline_runner.ts` (`runMultiStatePipeline`) drives `executePipelineGraph`; `pipeline_runner.ts`'s `runActivation` is the per-activation executor and owns only the agent run. Per agent-state activation, in strict order: durable `activation_started` → runtime input existence/regular-file/containment checks (`RuntimeInputError` → `runtime_input_missing`, before Session creation) → fail-closed activation control-tree preparation → re-resolution of every declared protected input against its recorded baseline (canonical target + `dev`/`ino` + digest, `WorkspaceInputError` → `protected_input_modified`, before Session creation) → a final synchronous `gate.checkAbort()` with no await before `createChildSession` (a signal recorded during the durable `start_activation` or the filesystem preparation can no longer create a Session) → create child Session → immediately durable `session_created` → pull image (non-fatal) → durable `agent_running` → verify the expected `result.json` is absent (`ControlPathError` → `control_path_invalid`) → `docker-helper run` with the state's `timeout_seconds` (signalable, SIGTERM at the deadline) → re-verify the full filesystem identity of all protected inputs (declared path re-resolved fresh; canonical target, `dev`, `ino`, digest) → verify the result identity (`run_id`/`state_id`/`activation_index`/`attempt`), schema, artifact confinement, and protected-input aliasing (against the confirmed baseline identity) → read `result.json` without following symlinks (regular non-symlink file inside the exact activation leaf, O_NOFOLLOW read) → durable `result_accepted` (digest + artifacts, never the summary) → delete the child Session exactly once → durable `session_cleanup_completed` → return only the validated outcome; the engine's transition-commit hook then records transition + cursor in one commit before the next callback. Sessions are never reused between states or revisits; the bearer stays in memory. Launcher authority is checked once per pipeline run; all profiles load before it. On failure the active Session is still deleted exactly once; a cleanup failure stops the pipeline with its prior priority; without a successful cleanup outcome no engine outcome is returned and no transition is applied; a signal blocks the next Session creation, and a signal during Session create lets the create finish, deletes the Session, and never runs the worker. Signal/timeout first-wins is shared with plain `smoke` through the `RunCauseGate` in `lifecycle.ts` (failure/cleanup boxes + the synchronous run-level cutoff before the single final state write); plain `smoke` keeps its existing behavior.
- Activation control tree (implemented): all orchestrator-side activation paths are built from the fixed canonical workspace recorded before Launcher auth — never from the raw CLI workspace alias — via `prepareActivationControlTree`: every parent component (`<ws>/.pipeline-agent-smoke`, `<runId>`, `activations`) is a real non-symlink directory (created 0700 if missing), the activation leaf `<index>-<stateId>` and its `attempt-1` child must be absent (an existing leaf, symlink, or unexpected object is a `ControlPathError` before any Session is created), the leaves are created as new directories with `mkdir` (no recursion, `EEXIST` rejected), and `execution.md` is written with `O_CREAT|O_EXCL|O_NOFOLLOW` so a pre-placed file or symlink is never followed or overwritten. The whole tree must still resolve inside the canonical workspace after preparation. Before the worker starts the expected `result.json` must be absent; after the run it must be a regular non-symlink file inside the exact activation leaf and is read through an `O_NOFOLLOW` file descriptor (`readResultFileNoFollow`); no external sentinel is ever created, modified, or read through a substituted control path.
- Protected-input binding (implemented): a baseline protected input keeps the declared pipeline path, the canonical target, `dev`, `ino`, and the digest as separate fields; the durable `protected_inputs[].path` is the declared path, not a rewritten canonical-relative alias. Directly before every Session and again after every worker run (before the result can be accepted), `verifyProtectedInputs` re-resolves the declared path fresh and requires canonical target, `dev`, `ino`, and digest to match the baseline; a retargeted in-workspace symlink, a replaced inode with identical bytes, a changed file type, a disappearance, or a content change fails as `protected_input_modified` (`WorkspaceInputError`), and a pre-activation mismatch creates no Session. An unchanged internal symlink remains acceptable. Artifact direct/symlink/hardlink checks run against the confirmed baseline identity of all protected inputs.
- CLI: `bun src/main.ts smoke|agent-smoke`. `agent-smoke` takes `--config-root ABSOLUTE_PATH` and optional `--pipeline-root ABSOLUTE_PATH` (default `/opt/orchestrator/pipelines/default`), `--workspace`, `--launcher-id`; `--profile` and `--task` are removed — the execution profile and the workspace input paths are selected only by the pipeline's agent states — and `--image` stays rejected (the image comes only from the selected profile). Plain `smoke` keeps `--image` and is unchanged. `agent-smoke` needs the docker-helper socket and a **Launcher** credential (never a Principal/admin credential) at `${XDG_CONFIG_HOME:-$HOME/.config}/docker-helper/credential.token`. Pipeline/plan/profile/input validation happens before Launcher auth: failures exit 1 with `runId: ""` and create no session.
- Agent worker input: the pipeline prompt travels only inside an orchestrator-owned per-activation execution document (`<run-dir>/activations/<activation-index>-<state-id>/attempt-1/execution.md`, non-secret: run id, state id, activation index, attempt, workspace-relative input/result paths, allowed outcome, prompt body, exact result format) written inside the existing run directory; the OpenCode command receives a short static instruction pointing at that document. Each activation's `result.json` lives next to it; a revisit cannot see a previous activation's result as its own. Prompt and input bodies never appear in argv, env, state, or orchestrator diagnostics; the pipeline bundle and config root are not mounted into the worker (workers get the workspace only). Each state's inputs are checked right before its activation (existence, regular file, inside the canonical workspace); unprotected inputs may be created by earlier states; a missing runtime input fails the run before that state's Session is created. After every agent run the digests of all protected inputs are re-verified and artifacts aliasing any protected input (direct, symlink, or hardlink) are rejected. The state's `timeout_seconds` is enforced only on the signalable worker `docker-helper run`: the runner sends SIGTERM at the deadline, marks the result timed out, and the run fails normally (exit 1, single cleanup); user SIGINT/SIGTERM keeps exit 130/143.
- docker-helper interaction: `session create/delete` and `pull`/`run` go through the **official CLI 2.1.0**, spawned as an argv array (`Bun.spawn`, no shell); the narrow `GET /auth` check stays a direct unix-socket call (the CLI has no equivalent Launcher-authority command). `session create/delete` run with a minimal filtered env (`HOME`, `XDG_CONFIG_HOME`, `XDG_RUNTIME_DIR`, `DOCKER_HELPER_CONFIG`); `pull`/`run` run with the child Session bearer only (`DOCKER_HELPER_SESSION_TOKEN`), which is repeated as `--env` so the worker receives its Session capability. Worker env values are passed as separate `--env KEY=VALUE` arguments; until docker-helper issue #3 is implemented, resolved worker env (including secrets and the OpenCode config content) is visible in the `docker-helper run` process argv — a consciously accepted temporary risk. They never appear in state files or the orchestrator's own diagnostics. Worker output is inherited from the CLI process: docker-helper 2.1.0 prints the (already mixed) container operation output on its stdout, and the CLI's own warnings/errors go to stderr; raw worker output is treated as untrusted (never a safe audit log or authoritative state); the orchestrator implements no polling, log cursor, or operation-API parsing.
- Cancellation contract: the first SIGINT/SIGTERM is recorded by the lifecycle; a running `docker-helper run` process receives the same signal (a bounded synchronous best-effort cancel inside docker-helper 2.1.0 — the orchestrator never confirms a terminal operation state) under a first-wins rule: the first terminal cause of the active signalable worker — runner `timeout` or `user_signal` — is recorded once; a user signal that wins suppresses the timer (`timedOut` stays false, exit 130/143), and a user signal that loses to the runner timer is neither delivered nor forwarded to the lifecycle (the run stays a timeout failure, exit 1). `killActive` returns whether the signal may still be recorded as a lifecycle abort; signals outside a worker run keep the plain lifecycle semantics. `session create`, `pull`, and `session delete` always run to completion. Cleanup (child Session delete) happens only in the single lifecycle `finally`, after the active hook settles — no fire-and-forget cleanup. The signal cutoff sits synchronously after cleanup and before the single authoritative final state write: causes are snapshotted and signal acceptance closes with no await in between, then exactly one `finalize` writes the already-decided terminal status; a signal delivered after the cutoff — including while the final write is in flight — is late and can no longer change the recorded outcome or the exit code, and the terminal run status is never rewritten.
- `--workspace` is the absolute host workspace path used by docker-helper; it must also be visible at that same absolute path inside the orchestrator container (the proven dual-mount pattern: mount the Session workspace twice — canonical host path + `/workspace`). Workers mount the Session workspace at `/workspace` (`source "."`); the host path need not be reproduced inside workers. A helper-launched container cannot receive the docker-helper socket (workspace-relative sources only), so a containerized orchestrator must be launched by the operator (plain `docker run` with socket + credential + dual mounts); this docker-helper limitation blocks the helper-launched UAT path until helper gains trusted socket projection.
- Decision-table substrate (pure, implemented, **not yet used by the production runner**): `orchestrator/src/decision.ts` implements a declarative decision-table format (YAML, `schema_version: 1`, exact-field validation), a fail-closed loader/compiler into a deep-frozen engine-owned snapshot, and a pure deterministic evaluator. Expressions are a closed boolean DSL (`{fact, equals}` / `{all}` / `{any}` / `{not}`) with static limits (64 facts/decisions/relations/constraints/rules, depth 16, 512 nodes per expression, 4096 total, 128-char ids). Evaluation order: fail-closed fact validation (missing/extra/non-boolean facts throw `DecisionModelError`, never `uncovered`) → relations in declaration order (`inconsistent_facts` with all violated ids in order) → allowed set narrowed by active hard constraints in declaration order (`only` intersects, `forbid` removes) → first rule whose `when` matches and whose decision is still allowed (matched-but-forbidden rules never terminate the search) → `uncovered` as a normal result (no fallback). Loader containment reuses the shared helpers from `orchestrator/src/bundle_file.ts` (extracted from `pipeline.ts` unchanged; `pipeline.ts` passes its error class and scope wording): absolute real-directory root, clean `.yaml`-only bundle-relative path, internal symlinks allowed, symlink escapes and lexical traversal rejected, regular files only. `pipelines/default/decisions/architect.yaml` is the runtime decision model mechanically transferred from `docs/pipeline-oracle/decision-table.json` (11 facts, FC1–FC6, HC1–HC5, 7 rules in original priority order, exact decision ids, no automatic fallback); source line references, explanatory text, stage effects, state writes, recovery semantics, and P01 are deliberately not part of it — P01 remains the next policy layer above the base evaluator. `orchestrator/tests/decision.test.ts` proves equivalence with the unchanged oracle over all 2048 boolean assignments in `bit_order` (1952 inconsistent, 82 selected with exact frozen decisions + rule ids via an independent transcription, 14 uncovered, exact distribution) plus generic unit tests (arbitrary non-legacy ids, limits, containment, snapshot immutability, repeated-evaluation determinism). `pipeline.yaml`, `pipeline_engine.ts`, `pipeline_runner.ts`, `agent-smoke`, the durable state schema, and the CLI do not reference any of this yet; wiring it into production is a later increment.
- Pipeline schema v2 data ports + activation layout planner (pure, implemented, **not yet used by the production runner**): `orchestrator/src/pipeline_v2.ts` implements the `schema_version: 2` compile branch as a separate, self-contained module. v2 describes data flow as named ports instead of workspace paths: run-level `inputs` (logical run inputs; host paths are bound later by CLI/API, never declared in the document) and run-level `outputs` (data handed to the user after completion, `required: true` outputs fail the run if absent at the terminal, optional outputs may be absent); every agent state declares local `inputs`/`outputs` ports; each port source has exactly one form (`{pipeline_input: ID}` or `{state_output: {state, output}}`); port types are `file`/`directory`/`json`; `json` ports require a bundle-relative JSON schema file (loaded through the same realpath containment, parsed as a JSON object, no generic JSON Schema validation). Pipeline inputs and agent outputs are the only places that declare a type or schema; agent input ports and run outputs derive both from their source — a run output is exactly `{id, required, source}` (declaring `type`/`schema` on it is rejected), and a stricter output contract is a separate transforming state, not a re-interpretation of the same value. The JSON contract travels by data flow: a run-level json input resolves and keeps its `schemaPath/schema`; an agent input port sourced from it (directly or through `state_output`) receives the derived type and the immutable schema snapshot value; schema paths stay with the declaring sites. Runtime semantics fixed in the module doc: a `state_output` value is the last successfully accepted output of the named state from an earlier activation; if none exists the run fails closed without fallback; self-references and cycles between state outputs compile (value availability is a runtime question); no user port paths, no mount targets, and `image`/`env`/`mounts`/`command`/docker/helper/session options remain forbidden; the activation completion envelope is orchestrator-owned and work products are the declared outputs only (no free-form artifact list). `loadPipelineV2` returns an engine-owned deep-frozen snapshot; `planActivationLayout(pipeline, stateId)` is a pure deterministic planner producing an immutable plan: ordered input ports (`source`, `type`, optional deep-frozen schema snapshot without `schemaPath`, fixed target `/pipeline/inputs/<id>`, `read_only: true`), ordered output ports (`type`, optional parsed schema snapshot, fixed target `/pipeline/outputs/<id>`, `read_only: false`), project mount `/workspace` RW, `reject_undeclared_outputs: true`, and only logical/structural data (no bearers, credentials, env values, host paths, or schema paths). Provenance is fail-closed before any target path is built: `planActivationLayout` first checks membership in a module-private `WeakSet` registry that only the fully resolved, deep-frozen snapshot returned by `loadPipelineV2` is registered in; hand-built objects, casts, shallow/deep clones (`structuredClone`), Proxies and corrupted objects are rejected with a stable `PipelineError` before any field is read (getters never run), and there is no second validation pass — structural correctness is owned once by the compiler. `stateId` remains a plain planner input (safe id + agent state of the trusted snapshot). `pipeline.ts` shares exact-field validators + `checkGraphShape` with v2 and rejects **any** YAML document with `schema_version: 2` at the production loader with exactly `pipeline schema version 2 is not executable yet` before Launcher auth and before any Session (no "genuine v2" shape sniffing). Session capability contracts are fixed next to the planner, unwired: Execution Session (`type: "execution"`, scope run root, orchestrator-only bearer, never passed to a worker in any form), Tool Session (`type: "tool"`, scope project only, bearer handed to the worker, nested containers cannot reach pipeline inputs/outputs; no wide-Tool-Session workaround exists), and the separate immutable Worker Launch contract (`WORKER_LAUNCH_CONTRACT`: worker launched via the Execution Session receives a projected helper socket — the socket is transport, the Tool Session bearer is the worker's authority); worker mounts project `/workspace` RW, prepared activation inputs `/pipeline/inputs` RO, activation outputs `/pipeline/outputs` RW; docker-helper#8 (allowed-roots RO/RW) is not required by this increment. `orchestrator/tests/pipeline_v2.test.ts` covers v1 regression, v2 compilation, exact-field/union validation, duplicate/unknown references, schema propagation through `state_output`, schema containment, frozen snapshots, planner determinism/targets/flags, plan secret/host-path/schema-path absence, planner fail-closed regressions (forged port ids, hand-built/cloned/proxied objects, getters never invoked, cyclic schemas, duplicate state casts), socket-transport/Tool-authority separation, and the production rejection before auth/session. The production runner, durable state, lifecycle, signal handling, helper transport, and the default bundle are untouched by this substrate; wiring v2 execution into `agent-smoke` is a later increment.

- Pipeline v2 run-input snapshots + activation data layout (pure host-side substrate, **not wired into the production runner**, no Session/container launch): `orchestrator/src/pipeline_v2_runtime.ts` is the v2 data plane. Run layout: `<runRoot>/project` is the shared project directory of the whole run — it must already exist as a real non-symlink directory before `snapshotRunInputs` is called, the runtime never creates, clears or copies it (preparing the initial project content is the caller's responsibility), and every activation mounts exactly this one directory at `/workspace` read-write, so changes persist across activations; there is no per-activation project directory. `snapshotRunInputs(pipeline, bindings, runRoot)` accepts the trusted `ResolvedPipelineV2` (provenance-checked via `requireResolvedPipelineV2Provenance` — no second compiler), the full binding list `{id, path}`, and an absolute orchestrator-owned `runRoot` that must already be a real directory (symlinked final component rejected; symlinked ancestors canonicalize through `realpath`) whose `project/` subdirectory exists as a real non-symlink directory. Every declared pipeline input is bound exactly once (missing/duplicate/unknown rejected before any mutation), each binding path must be absolute, its real object kind must match the declared `file`/`directory`/`json` type (`json` = regular file with valid JSON; the value must additionally conform to the loader-compiled Draft 2020-12 schema when the input declares one — the immutable schema snapshot already carried by the resolved pipeline is used, schema paths are never re-read), a symlink binding is rejected, and a binding resolving inside the canonical run root is rejected. Every input is copied into the orchestrator-owned snapshot `<runRoot>/data/inputs/<input-id>`: file/json byte-for-byte, directories recursively in deterministic relative-path code-unit order with only real directories and regular files allowed (symlink/FIFO/socket/device entries rejected fail-closed). Each input digest is a deterministic SHA-256 over the declared type, relative paths and content only (8-byte big-endian length framing, fixed domain tag `pipeline-v2-input\0`; directory entries contribute their kind tag `directory\0`/`file\0`, their length-framed UTF-8 relative path, and the length-framed content for files — names, entry kinds, and empty directories all change the digest; `sha256` hex) — never host paths, inodes, permissions or timestamps. File/json snapshots are written to a temporary name inside `data/inputs` and published atomically via `link()` (EEXIST-safe); directory snapshots are built in a temporary directory and published with one `rename()` (never replaces a file/symlink/non-empty directory). On failure the operation removes exactly the objects it created (tracked, best-effort, containment-guarded), so no partial snapshot becomes authoritative and existing snapshots (any pre-existing target object) are never overwritten; on success the returned deep-frozen metadata (`RunInputsSnapshot`: canonical `run_root`, `inputs_root`, canonical shared `project_root`, ordered per-input `{id, type, protected, snapshot_path, digest}`) is the run's only data source and user source paths are never read again. Honest boundaries: no protection against a trusted host process mutating a source during the read; a crash (SIGKILL) mid-copy leaves leftovers that make a retry fail closed; files are fsynced but no crash-durability claim is made. Snapshot provenance: the frozen snapshot object is registered in a module-private `WeakMap` together with the exact trusted pipeline object and the canonical run/project roots, only after the full snapshot succeeded; `prepareActivationData` accepts only that exact object (identity check against the same `ResolvedPipelineV2` object it was handed) and rejects hand-built objects, casts, spread/`structuredClone` clones, Proxies (getters never invoked) and snapshots of another pipeline with a stable `PipelineError` before any field is read — there is no second structural re-validation pass, and a future resume loader could mint trusted runtime state through the same registration path. `prepareActivationData(pipeline, runInputs, acceptedOutputs, stateId, activationIndex)` prepares a fresh `<runRoot>/activations/<index>-<stateId>/data/` tree with `inputs/` and `outputs/` only — there is **no per-activation project directory**; the shared `<runRoot>/project` directory is mounted at `/workspace` RW by every activation and is never created, cleared, copied or removed by the runtime (preparing the initial project content is the caller's responsibility). `inputs/` is copied per declared port strictly in declaration order (pipeline inputs only from the run-owned snapshot; state outputs only from the explicitly passed runner-owned accepted records `{state, output, activation_index, digest}` — no user paths and no types are accepted: the type is derived from the declared output port and the object must exist at the fixed orchestrator-derived path `<runRoot>/activations/<index>-<state>/data/outputs/<output>` with real non-symlink parents, matching real kind, and canonical containment; before anything is prepared the run-input snapshot is re-verified in full at its fixed orchestrator-owned paths (`verifyRunInputsSnapshot`: every entry a real non-symlink object of its declared kind resolving exactly to its recorded snapshot path inside the canonical run root, directory snapshots containing only real directories and regular files, every digest recomputed with the `pipeline-v2-input` framing and compared — a modified, relocated or escaped snapshot fails before the accepted history is parsed and long before the activation leaf is created; the original user binding paths are never read again), then the whole accepted history is validated — every record, including old and non-winning ones, is resolved to its fixed location and its digest is recomputed with the exact output-domain framing and compared, and only after the whole history checks out is the winning record per `state`/`output` pair selected by highest activation index independent of list order; so an accepted output that changed after acceptance — content, entry name, empty directory, kind or JSON bytes — fails the next activation before its leaf is created; missing/forward/first-visit self references fail before anything downstream; duplicate records and one activation index spanning two states are rejected; for every recorded `{activation_index, state}` pair the record set must be exactly the declared output ports of that agent state, so a partially constructed runner history is rejected as incoherent before any location is resolved; records with an index not below the current activation index are rejected; digests must be lowercase SHA-256 hex), `outputs/` (an empty 0700 directory pre-created for `directory` outputs; `file`/`json` output paths deliberately absent until a worker run). The activation index is globally unique within the run: before the leaf is created, any existing `activations/` entry with the same `<index>-` prefix (any state id, any object kind, never followed, unmodified) rejects the request. The returned immutable layout contains exact mount descriptors — shared project `/workspace` RW, inputs `/pipeline/inputs` RO, outputs `/pipeline/outputs` RW — and may carry canonical host paths (orchestrator-internal; they never enter the compiled pipeline, prompt, envelope or durable state), plus no bearer/credentials/env/helper endpoint/Docker options/argv. The prepared layout is registered in a module-private `WeakMap` (pipeline + canonical run root) after success; only that exact object can later be passed to `acceptActivationOutputs` for the same pipeline object. Accepted records are a trusted runner-owned input (agent envelopes, stdout and worker files can never create records; the production link to durable `result_accepted` is not implemented); nothing accepts an agent-declared "output is ready". Directories 0700, files 0600; worker-UID compatibility of the output tree is an explicit limitation for the next runtime increment (no 0777 workaround). `orchestrator/tests/pipeline_v2_runtime.test.ts` covers the exact binding set, type mismatches for all three types, json run-input schema violations rejected before any mutation, snapshot immutability after source change/deletion, digest determinism and framing, declaration-order processing, symlink/FIFO/socket rejection, pipeline-input activation, state-output handoff through acceptance-minted records, highest-index-wins under record permutation, missing/future/current and first-visit self outputs, global activation index uniqueness, accepted-record shape/declaration/index/fixed-location validation, arbitrary contained paths never satisfying records, symlink traps + sentinel preservation, forged snapshot batteries (clone, forged paths/digest/protected, duplicate entries, other-pipeline snapshot, getter/Proxy never invoked, rejection before filesystem mutation), accepted-history digest verification (readable-then-unreadable outputs), the shared project root across activations, frozen results, failure cleanup, v1 regression, and the unchanged production v2 rejection before auth/session.
- Output acceptance for one prepared activation (pure host-side, **not wired into the production runner**): `acceptActivationOutputs(pipeline, activation)` in `orchestrator/src/pipeline_v2_runtime.ts` validates the completed `outputs/` tree of one prepared activation and returns one deep-frozen trusted record per declared output in declaration order — exact fields `{state, output, activation_index, digest}`, no path/type/schema/summary/timestamps/content. The argument must be the exact `PreparedActivationData` object a successful `prepareActivationData` call returned for the same `ResolvedPipelineV2` object (registered after success in a module-private `WeakMap` together with the pipeline and canonical run root; hand-built objects, casts, spread/`structuredClone` clones, Proxies with traps never invoked, and activations of another pipeline are rejected before any field is read and before any filesystem access). Acceptance creates, fixes, renames and deletes nothing — it only reads the finished tree. The outputs root is re-examined fresh (the worker held it read-write): it must be a real non-symlink directory resolving exactly to itself inside the canonical run root, its top-level entries must be exactly the declared output ports of the state (a missing declared output fails, any undeclared top-level entry fails, no duplicate/alias/fallback semantics; names, paths and types come only from the compiled pipeline and the prepared layout — the agent never reports them; `reject_undeclared_outputs: true` is a real enforced invariant since this increment), and each output must be a real non-symlink object of its declared type whose canonical path stays inside the outputs root. `file` outputs are existing regular files with non-symlink final components read through `O_NOFOLLOW`; `json` outputs must additionally be valid JSON conforming to the declared, loader-compiled Draft 2020-12 schema (no coercion, no defaults, nothing removed, the parsed value is never modified); `directory` outputs are real non-symlink directories whose recursion allows only real directories and regular files (symlink/FIFO/socket/device entries fail). All parents and canonical paths stay inside the canonical run root and the exact activation outputs location. Each record carries a lowercase SHA-256 digest over the separate domain `pipeline-v2-output\0` plus the declared type, with the same unambiguous framing as input digests (length-framed bytes for file/json; kind tag, length-framed UTF-8 relative path, length-framed file content in code-unit sorted order for directories — names, entry kinds and empty directories participate; host paths, inodes, permissions and timestamps never do). Accepted records remain a trusted runner-owned input; a changed accepted output (bytes, name, empty directory, kind, JSON bytes) is detected by digest recomputation before the next activation leaf is created. Diagnostics never contain file contents or JSON values. JSON Schema mechanism: `orchestrator/src/pipeline_v2_schema.ts` wraps the pinned Ajv Draft 2020-12 dialect (`ajv` 8.17.1, `orchestrator/package.json` + `orchestrator/bun.lock`; installed into the image by `Dockerfile_orchestrator` via `bun install --frozen-lockfile --production`). Schemas are compiled only at trusted `loadPipelineV2` time, before the resolved snapshot is registered (compile failure rejects the load); a fresh Ajv instance per compile keeps schemas hermetic; internal `$ref`/`$defs` are supported, remote/missing refs and unknown format keywords fail compilation, `strictRequired` is off (a required-only object schema is valid Draft 2020-12), no network, no remote loading, no executable callbacks, no coercion/defaults/removal. The dialect is synchronous-only: a schema that compiles to an async validator (`$async`) is rejected inside compile before registration (a `$async` subschema behind an internal `$ref` fails Ajv compilation outright), `validatePipelineJson` re-checks `$async` defensively before calling, and success is only the literal boolean `true` — `false` is an ordinary validation failure and a Promise/thenable result can never pass as success, so no unhandled rejection can be created. Validation errors are rendered value-free as `<instance path>: <message>`. Runtime `JSON.parse` diagnostics for user data values (json run inputs, json activation outputs) are normalized to the stable content-free form `<what> <path> is not valid JSON` — no parser message, offending token, line/column, or input fragment ever enters the message (schema-file parse errors in the trusted bundle keep their compile/load diagnostic). - Run-level output publication at the terminal (pure host-side, **not wired into the production runner**, no Session/container launch): `collectRunOutputs(pipeline, runInputs, acceptedOutputs)` in `orchestrator/src/pipeline_v2_runtime.ts` materializes the declared run-level outputs after the graph runner has reached a terminal — deciding whether a terminal may be entered is the graph runner's job, and the function takes no terminal id, no user paths, no types, no mounts and no Docker options (arity 3: trusted pipeline, trusted run-input snapshot, runner-owned accepted history). ## Hard invariants

- Never mount `docker.sock` into the orchestrator or agent containers; docker-helper is the only Docker access path.
- Images must not bake in provider credentials or OpenCode model config.
- The agent worker env is built from **exact bindings declared by the selected trusted profile** (`orchestrator/src/profile.ts`), plus explicit orchestrator-owned run params (`OPENCODE_CONFIG_CONTENT` from the profile's OpenCode config, the child session bearer, `AGENT_SMOKE_*` run identity). No ambient inheritance. Control variables (`DOCKER_HELPER_*`, `AGENT_SMOKE_*`, `ORCHESTRATOR_*`, `OPENCODE_CONFIG_CONTENT`) and operator path variables (`HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`) can be neither profile destinations nor sources; launcher credentials, admin tokens, and the orchestrator state path are never forwarded. Keep `orchestrator/src/main.ts` usage text and tests in sync when touching the contract.
- For `agent-smoke`, exit code 0 or agent JSON events alone never mean success: validate the per-activation `result.json` schema (exact fields only, schema version 2), the `run_id`/`state_id`/`activation_index`/`attempt` identity, artifact existence and workspace confinement (including symlinks), unchanged protected inputs, and the outcome transition to a success terminal before accepting the result.
- Every created child Session must be cleaned up on all controlled exit paths, including errors and cancellation. Cleanup failure makes the overall run unsuccessful, even when the worker succeeded.
- Trusted execution profiles: implementation and deterministic tests are complete; the end-to-end profile-backed `agent-smoke` UAT (real launcher credential, real docker-helper, real OpenCode/LLM run) is still pending. Do not describe profiles as a proven baseline in docs until that UAT passes.
- `base`/`go26`/`dotnet10`/`orchestrator` run as non-root `opencode` user (uid/gid 1000); `gdk` follows its upstream GDK image user model.
